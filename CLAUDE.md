# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

MarketPressure is a quantitative swing-trade screener for B3 (the Brazilian stock exchange) built around the "Garrafa de Gás" setup: a pullback to a moving average inside a rising MM200 trend. It scans the B3 assets above a liquidity floor (about 260: stocks, listed funds, ETFs and BDRs) and ranks the top 20 of each asset type by Score Composto, in one table per type. A second tab, "Carteira", tracks the user's portfolios (B3, US and crypto positions, dividends, configurable classes with allocation targets, a contribution calculator and time-weighted return against CDI and BOVA11). Locally there's no build step; the only dependency is `pyarrow` (`requirements.txt`), used by the Parquet database in `data/`. Tests use the standard library's `unittest` (`tests/`). UI text and identifiers are in Portuguese (pt-BR).

The same code is also published on Cloudflare Workers at `marketpressure.lucasaraujo.dev.br` with no Python server: the browser runs the `marketpressure` package itself (Pyodide), and a small Worker serves the files, relays the data sources and keeps the database in D1 (see "Publicação (Cloudflare)").

Run it:

```
pip install -r requirements.txt               # pyarrow (once)
copy .env.example .env                        # once; fill in BRAPI_TOKEN
python server.py                              # or: python -m marketpressure; then open http://127.0.0.1:8765
python -m unittest discover -s tests -t .     # tests (offline, temporary database)
npm install && npm run dev                    # published version locally (wrangler dev on :8787, local D1)
```

Layout:

```
server.py            launcher (python server.py), same as python -m marketpressure
marketpressure/      Python package: all calculations, data access and the HTTP server
web/                 what the browser receives: the pages (Screener, Carteira, Backtest, Conta, login) and assets/ (css, js)
data/                the database (Parquet tables, never served, not versioned)
tests/               unittest suite (support.py: temporary database + synthetic candles)
.env / .env.example  local settings and secrets (BRAPI_TOKEN); .env is not versioned
worker/              Cloudflare Worker of the published version: index.js (/proxy, /db, static files, login gate), auth.js (/auth: login, sessions, accounts), schema.js (D1 tables)
scripts/create-user.mjs  creates an account directly in D1 (how the admin was created)
scripts/build.mjs    builds dist/ for Cloudflare (web/ + the Python package); dist/ is not versioned
wrangler.jsonc       Cloudflare config (assets, D1 binding, custom domain); package.json pins wrangler
```

**Configuration** lives in `marketpressure/config.py`: paths (`ROOT_DIR`, `WEB_DIR`, `DATA_DIR`), `HOST`/`PORT`, `LOG_LEVEL`, `BRAPI_TOKEN` and the cache TTLs. Each value can come from an environment variable or from `.env` at the project root (`MARKETPRESSURE_HOST`, `MARKETPRESSURE_PORT`, `MARKETPRESSURE_DATA_DIR`, `MARKETPRESSURE_LOG_LEVEL`, `BRAPI_TOKEN`; the environment wins over `.env`). Never put secrets in code. Without `BRAPI_TOKEN` the stock list comes from the `universe` table (warning in the log).

The pages share an app bar (`header.appbar`: the "MarketPressure" brand, `nav.tabs` and `.tabs-user`; the same markup in the four pages) whose tabs have an inline SVG icon above the label, banking-app style (relative links, `aria-current="page"` on the active tab, shown in the accent color with an indicator line). On desktop it sits at the top; at ≤ 640px the tabs become a bar fixed at the bottom of the screen (the body gets bottom padding for it) and the header keeps only the brand and the user. "Screener" is `/` (`analise_quantitativa_b3.html`), "Carteira" is `/carteira` (`carteira.html`) and "Backtest" is `/backtest` (`backtest.html`) and "Configurações" is `/configuracoes` (`configuracoes.html` + `configuracoes.js`: the sell strategy, see "Estratégia de venda"). In the published version the bar also shows "Conta" (`conta.html`), the user's name and "Sair" (elements marked `data-auth`, shown by `core.js` after `/auth/me`); locally there is no login and they stay hidden.

The page also works when opened from another dev server, such as VS Code Live Server on port 5500. Its API calls go to `http://127.0.0.1:8765`, and the server answers CORS for **local origins only** (`ALLOWED_ORIGIN`: `http(s)://localhost` or `127.0.0.1` on any port, echoed in `Access-Control-Allow-Origin`); any request with another `Origin` gets 403, so a website open in the browser can't read or change the portfolios. The server must still be running.

## Division of work: Python computes, JavaScript displays

**All calculations live in Python on the server. JavaScript is only for the front end: API calls, rendering, events, tabs, the chart and formatting.** Do not add calculations, business rules, validations or data changes to the `.js` files; add them to the Python modules and expose the result through an `/api` route. Classifications that turn numbers into a category (regime, estado da garrafa, situação, status of an aporte row) and texts derived from the analysis (the screener's justificativa, validation and confirmation messages, target warnings) are also made in Python; JS only maps the returned key to a badge/text.

Python modules, all in the `marketpressure/` package with relative imports (standard library, plus `pyarrow` in `database.py`, imported only when the Parquet backend is used). Layers, each using only the ones below it: `server`, `browser` → `api` → `ai_prompt`, `backtest_prompt` → `portfolio_prompt`, `portfolio_backtest` → `screener`, `portfolio_store` → `portfolio_service` → `goals`, `portfolio` → `market_data` → `database` → `core`, `config`, `runtime`:

- **`config.py`**: settings (see above).
- **`runtime.py`**: where the code runs. `BROWSER` (`sys.platform == "emscripten"`, i.e. Pyodide), `REMOTE` (database in D1 through `/db` and sources through `/proxy`: true in the browser or after `use_remote(base_url, token)`, which the daily update uses outside the browser, with `urllib` and the service token), `run_all(fn, items)` (threads on the server, sequential in the browser, which has none; use it instead of `ThreadPoolExecutor`) and `http_request(method, url, body)` (synchronous same-origin XMLHttpRequest, allowed inside a Web Worker).
- **`core.py`**: B3 clock (`market_clock`, `day_of`, `today_iso`, `session_in_progress`, `closed_candles`, `iso_day_in`, `local_time`), indicators (`sma`, `ema`, `rsi`, `stochastic`, `bollinger_width`, `obv`, `atr`, `compute_indicators`, which returns an `Indicators` dict where `stoch` and `bbw`, used only by `pressure`, are computed on first access (`LAZY_INDICATORS`)), `SETUP`, `candle_pattern`, `evaluate_setup`, `exit_signal`, the partial-sale timing (`EXIT`, `STRENGTH`, `trend_strength`, `PARTIAL_TIMINGS` = `alvo` | `forca`, `weak_close(ind, i, goal)`: the close is at or above the target and the rally has no strength), and helpers (`add_up`, `avg`, `js_round`, `clamp01`, pt-BR formatters `fmt_num`, `fmt_brl`, `fmt_qty`, `fmt_date` used in messages). Windows has no time-zone database and the project uses no packages, so the three zones are computed by hand: São Paulo is fixed UTC−3 (no DST since 2019; in the older years of the history the B3 daily candle is stamped 10:00 local, far from midnight, so its day doesn't change), UTC, and Europe/London with the EU DST rule.
- **`market_data.py`**: the fetchers and the in-memory cache (`cached`), `load_universe`/`universe` (the asset list: Yahoo's screener for the SAO exchange, `load_yahoo_list`/`yahoo_screener`, which needs the fc.yahoo.com cookie and a "crumb" (`_yahoo_auth` locally; published, the Worker's `/proxy` does it for a POST to `YAHOO_SCREENER`); name and sector from brapi (`load_brapi_stocks`) when it knows the ticker; without Yahoo (it sometimes refuses the session with HTTP 429), the saved `universe` table when it came from Yahoo (it has every type), else brapi's stocks, else any saved list; a fallback list is never written over the saved one), `asset_kind(ticker, shortName, longName)` (`acoes`: suffixes 3–8 and units ("UNT" in the short name); `fundos`: final 11 with FII/Fiagro/FI-Infra words in the name; `etfs`: final 11 with "Índice" in the name, minus `ETF_EXCLUDED_WORDS` (fixed income, crypto, leveraged/inverse); `bdrs`: suffixes 31–35 and 39; anything else `None`, left out), `drop_bad_candles` (an isolated close more than 50% away from the median of the 5 closes before and of the 5 after is Yahoo bad data and is dropped, with a warning; used by `history`), `adjust_splits` (a split or reverse split Yahoo left unadjusted — the open and the close jump by an integer ratio 1:k or k:1, k 2–`SPLIT_MAX_FACTOR` (50), within `SPLIT_TOLERANCE` (3%), with both price levels stable over `SPLIT_CONFIRM` (5) sessions — divides the earlier prices and per-share dividends by k and multiplies the volume, with a warning; e.g. SPXI11 1:8 on 2026-01-22; real crashes such as AMER3's −77% don't match an integer ratio; used by `history`, after `drop_bad_candles`; portfolio transactions are not adjusted), `load_history`/`raw_history` (Yahoo, raw route format, from the saved history plus only the missing part, see "Saved history"), `history(ticker, market)` (candles as `{date, o, h, l, c, v, adj}`, filtered and sorted; crypto and FX re-stamped by `restamp_days`), `load_cdi`/`cdi`, `load_proventos`/`proventos`. Any failure of an external source (network, timeout, HTTP error, invalid JSON, no data) raises `UpstreamError` (`http_json` wraps them), which the server turns into 502. In the browser `http_json` goes through the Worker's `/proxy?url=` (`proxy_url`), and a response already fetched by JavaScript can be handed in with `prime(url, status, text)`; `history_url` builds the Yahoo URL.
- **`screener.py`**: `CONFIG`, `pressure` and its helpers, `backtest_lots`/`lot_return`/`backtest`, `backtest_view` (the Backtest page), `analyze_asset`, `analyze_ticker`, `run_scan`, `build_ranking`, `analyses_for`, `views`, `bottle_state`, `regime`, `justification`, `ScanJob` (`scan_job`) and `bova_kpi`.
- **`ai_prompt.py`**: the text of the screener's "ANALISAR ATIVO" button (`build(scan, payload, ticker, mode, strict, lots, settings)`, settings = `strategy.load()`): the role (a very experienced medium/long-term analyst who speaks plainly and knows the perfect entry rarely comes), the task (start with COMPRAR AGORA / COMPRAR COM POSIÇÃO MENOR / EVITAR — there is no "esperar"; entry for today, invalidation, targets, position size, the concrete reason to avoid, risks, confidence), `DECIDE` ("Como decidir": the default is to buy; waiting for confirmation cost ~3 p.p. per buy in the app's portfolio backtests; EVITAR only for concrete reasons — trend breaking, falling knife, news shock, extreme volatility, a serious fundamental fact; be even slower to veto international assets; the asset's history is a datum, never a veto alone; why there is no stop loss — fixed and trailing stops didn't raise the profit consistently and cut the big winners, so the AI must not suggest a short stop — the numbers come from the backtests of Oct/2026), position size (the normal buy is 7.5–10% of equity, up to 1.5x — about 15% — with priority, never more: larger slices did much worse in the robustness tests), `EVENTS` ("Eventos e fundamentos", shared with `portfolio_prompt`: the app only reads price and volume, so the AI must search the news of each asset it recommends — by ticker and name, again with other terms when empty; an empty search is not "no news" and lowers the confidence; fundamentals weigh as a complement in three levels: events that lock the price (tender offer/OPA, delisting, merger or sale of control with a set price, judicial recovery, suspension) veto the buy even with priority/Top 5 — a flat price glued to the offer with a very low ATR looks like a perfect pullback, as DESK3 in Oct/2026; a grave fact (fraud, default, dilution…) means a smaller position or, if the thesis broke, EVITAR; fundamental opinion (valuation, sector, known results) never vetoes, at most resizes), the method, the ranking row (rank, Score, price, tested MA, pressure and its components/details, the asset's history with closed/open/recent buys both ways, the mean of the type's Top as reference, bottle, `advice` as "Indicação automática do app (regra fixa, só um dado)", justification), indicators from the history (MAs, slope, RSI, Stochastic, MACD, ATR, pullback top/low, 52-week range, returns, last 10 sessions), the type's regime, BOVA11, the sell rule of the asset's type and the portfolio's open buys. `ValueError` when the ticker is not in that ranking view.
- **`portfolio_prompt.py`**: the text of the Carteira's "ANALISAR CARTEIRA" button (`prompt(portfolio)` → `{name, text}`, `build(portfolio, analysis, settings)` on `portfolio_service.full_analysis(reuse=True)`): the same `ROLE` as `ai_prompt`, the task (health diagnosis with a 0–10 score, then MANTER / AUMENTAR / REDUZIR / VENDER per asset, next steps, risks, confidence), `DECIDE` (sell only by the configured exit rule or a grave concrete fact; why there is no stop loss (same text as `ai_prompt`); rebalance through contributions; internationals only on reversal; a holding under a price-locking event is not increased: sell now or accept the offer, whichever pays more; the priority never overrides a veto); partial sale and reversal-only tied in the robustness tests, so neither is switched for a recent result; weak periods are normal (below the CDI in 2021–23, about −40% in Covid) and the 60/40 mix beat 100% stocks in every start; the same position-size rule, `EVENTS` (same text as `ai_prompt`), the method, then the data: KPIs and returns against CDI/BOVA11, concentration, allocation per class vs target, the sell rule of each class, each open position (Situação and its reason, setup, place in today's Screener ranking — `fechamento`, `padrao`, loose — open lots, MAs/slope/RSI/ATR/returns/52-week range from the closed candles in the asset's currency), the Screener ranking of **only the classes with a target above 0%** (`_screener_section`: each ranking row goes to the class of its sell-rule group, `screener.rule_group`, so BDRs and ETFs from abroad fall in Internacionais; per row rank, Score, pressure, bottle, 10-year and 3-year backtest, the Screener's Indicação with the portfolio's open lots and whether it is held; US and crypto have no ranking, which the text says; the saved scan is re-read with `ScanJob._reload`), fixed income, dividends and BOVA11.
- **`backtest_prompt.py`**: the text of the Backtest page's "ANALISAR BACKTEST" buttons, one per result type: `single(view, exit_mode)` (Um ativo, `screener.backtest_view`), `portfolio(result)` (Carteira, `portfolio_backtest.run`) and `robustness(result)` (Testar robustez) → `{title, text}`. Each starts with `ROLE` (a quantitative analyst and investor, sceptical of backtests but fair), `TASK` (ROBUSTO / PROMISSOR / FRÁGIL / INCONCLUSIVO with a 0–10 grade, quality of the rules — `RULES_FOCUS` per type —, risks and biases, up to 5 improvements testable in the Backtest page, next test, confidence), `_method()` (the strategy rules from `CONFIG`), `_options()` (every field and option of the Backtest page, so the AI only suggests tests the user can run; update it when the form changes) and `TESTED` (what the app's portfolio backtests already tested and discarded, so the AI doesn't suggest it again; update it when new tests change a conclusion), then the configuration and every number of the result (metrics per strategy, year by year, profit concentration, lots/trades tables up to `MAX_LOTS`/`MAX_TRADES`, robustness periods). Results are cached by `remember`/`recall` (`cache_key` = type + today + validated params, `CACHE_SIZE` 6; `run_portfolio(params, fn)` for `pb.run`/`pb.robustness`), so the button doesn't run the backtest again; `api` stores every backtest it computes there.
- **`portfolio.py`**: every Carteira calculation, **pure only** (no network or disk): positions, open lots and the partial sale (`open_lots`, `partial_to_sell`), series, allocation, targets, the aporte plan, validations, `batch_totals`, `has_entries`.
- **`portfolio_backtest.py`**: the Backtest page's "Carteira" mode: `parse_params` (form → validated params, `ValueError` with the message), `universe_assets` (every asset of the type in the saved B3 list, `universe` table, not only today's liquid ones; or a typed list), `signals` (per asset and day: whether it would be in that day's screener ranking — 20-session traded value above the type's floor, fixed-income ETF range, setup — the Score of that day computed only with the past, and the rule-B exit; `{"illiquid": True}` when it never had the liquidity; cached in `_signals_cache`), `daily_ranking` (top N of each type by Score), `simulate` (one shared cash that buys that day's ranking) and `run` (both strategies + BOVA11 and CDI with the same flows, comparison and trades).
- **`goals.py`**: the Metas sub-tab, **pure only**: `goal_from_form` (validation), `target_capital`, `rates`, `simulate`, `months_to_reach`, `required_monthly`, `project` (everything a goal card shows), and for goals that start from the portfolio `tracking` (realized × planned since `created`), `average_contribution` (mean net monthly contribution of the last 12 months, from `portfolio.net_flows`), `annualized_return` (the portfolio's 12-month return, annualized; ≥ 90 days) and `projections` (time to reach by the plan, the real contribution, the real return and both).
- **`portfolio_service.py`**: loads quotes/CDI/dividends through `market_data`, calls `portfolio.py` and builds the page payloads: `structure`, `asset_info`, `quote_history`, `price_on`, `load_histories`, `full_analysis` (with the per-portfolio reuse cache), `analysis_payload`, `contribution`, `receivables`.
- **`database.py`**: the application's database (see "Database" below): `SCHEMAS` (`{column: "string"|"float64"|"int64"|"bool"}`), `read_table`, `read_tables(names)`, `write_tables` (server: Parquet, all temp files first, then `os.replace`, `backup=True` copies the previous files to `data/backup/`; browser: the Worker's `/db` on D1, one transaction, values checked against the column types by `_coerce`), `exists`, and `flatten_analysis`/`unflatten_analysis` for the screener analyses.
- **`strategy.py`**: the sell strategy chosen in the Configurações tab, **per asset group** (`GROUPS` = the fixed Carteira classes with a rule, `portfolio.CLASSES`: `acoes` Ações, `fundos` Fundos imobiliários, `etfs` ETFs Brasil, `internacionais` Internacionais — BDRs, ETFs from abroad, US and crypto): each group follows `parcial` (sell `fraction` of each buy at +`target`, the rest on the trend reversal), `forca` (after a buy reaches +`target`, sell `fraction` at the open after the first close that is still at or above the target with the rally without strength, `core.weak_close`; the rest on the reversal) or `reversao` (sell 100% on the reversal); target and fraction are shared (`PARTIAL_KEYS`, `TIMING`, `timing(rule)`, `partial_fraction(rule)`). Settings = `{target, fraction, kinds: {group: rule}}`; `DEFAULT` = `core.EXIT` with `forca` for `acoes` (the portfolio backtests of Oct/2026, 60/40 with income tax: it beat the partial at the target in 7 of 8 starts and the reversal alone in 8 of 8, 5 of 7 three-year windows; confirming the loss of strength over 2, 3 or 5 sessions did not help), `parcial` for `fundos`/`etfs` (not tested with `forca`) and `reversao` for `internacionais` (`INTERNATIONAL`: in the portfolio backtests the +10% partial sold the international winners too early). A saved choice is kept: the new default only applies to groups the user never saved. Tables `settings` (one row: target, fraction and the old single rule, which still applies to every group until the user saves again) and `settings_kinds` (`kind` = group, `strategy`; the old `bdrs`/`exterior` rows map to `internacionais`, `LEGACY_GROUPS`); per user when published. `for_group(settings, group)` → the rule `{key, target, fraction, group, timing}` that the Carteira and Screener functions take; `group_of(kind, market, name)` (outside B3, BDRs and ETFs from abroad by name → `internacionais`; used by the Screener, `screener.rule_group`, and the Backtest); `asset_rules(settings, classes)` → `(ticker, market) → rule` for the Carteira (the group of the asset's class; without one, by type); `screener_kinds` (what changes the ranking); `from_form`, `load`, `save`, `describe` (with `kinds: [{group, groupLabel, hint, key, label, text}]`), `describe_one`, `payload`.
- **`portfolio_store.py`**: reading/writing the portfolio tables (`read_raw` builds the document from the six tables, `doc_tables`/`write_doc` split it back, written together with a backup), `read_doc` (always migrated by `normalize_doc`) and every change as an **action** (`ACTIONS`, `apply_action`). Validation failures raise `ActionError` and nothing is written.
- **`api.py`**: the `/api/*` routes, with no HTTP. Each route is a short function registered with `@route(method, pattern)` (named groups such as `(?P<id>...)` arrive in `req.params`; `req.arg(name)` reads the query string, `req.json()`/`req.json_object()` the body). `call(method, path, query, read_body)` → `(status, payload)` maps errors in one place: `HTTPError` → its status, `ActionError` → 400 (with `extra`, e.g. `rowErrors`), `UpstreamError` → 502, `OSError` → 500 (database), anything else → 500 logged with the traceback (`log.exception`); 404 for an unknown path, 405 for a known path with another method. Also `clean`.
- **`server.py`**: the local HTTP server: origin check, static files and `api.call`. `main()` sets up `logging`, starts `daily_update` (a thread that, outside session hours, calls `scan_job.status()` at startup and every 10 minutes, so a scan older than the last close is redone once after the close) and `ThreadingHTTPServer`.
- **`update.py`**: the daily update, `python -m marketpressure.update` (see "Daily update"). Not copied to the published build.
- **`browser.py`**: the bridge used by the published version (Pyodide in `py-worker.js`): `handle(method, path, body_text)` → JSON `{status, body}` through `api.call`, and the screener scan in steps (see "Publicação").

Other modules log through `logging.getLogger(__name__)`; never swallow an exception silently (`except: pass`), log it with `log.warning(..., exc_info=True)` at least.

Number handling mirrors the old JS exactly: `add_up` sums left to right (Python's `sum()` of floats is compensated since 3.12 and can differ in the last digit), `js_round` is `Math.round` (Python's `round()` is banker's), `to_fixed` is `toFixed`, and `fmt_num` rounds half-up on the exact binary value like `toLocaleString('pt-BR')`. Keep these when porting or changing formulas.

## Why there is a Python server

- The free brapi plan allows **1 ticker per request** and only **ranges up to 3mo**. Only the test tickers PETR4, VALE3, ITUB4 and MGLU3 get longer ranges. MM200 and the backtest need several years of history (the server asks Yahoo for 10 years, ~2,490 daily candles), so brapi is used only for the stock list (`/api/quote/list`), which the free plan allows: the sector of the stocks and the fallback when Yahoo's list fails (the asset list itself comes from Yahoo's screener).
- Daily history comes from Yahoo Finance (`query1.finance.yahoo.com/v8/finance/chart/{TICKER}.SA`). Yahoo sends no CORS headers, so the browser can't call it directly.
- The server also does all the calculations (see above).
- The code holds no secrets; the brapi token comes from `.env`/the environment (`config.BRAPI_TOKEN`) and never reaches the front end. The server serves the two pages (`PAGES`: `/`, `/analise_quantitativa_b3.html`, `/carteira`, `/carteira.html`), the files under `web/` whose extension is in `CONTENT_TYPES` (`.html`, `.css`, `.js`, `.svg`, `.png`, `.ico`; the resolved path must stay inside `web/`) and `/api/*`. The code, `.env` and the database in `data/` are outside `web/`, so they are never served (404). A new front-end file just goes in `web/assets/js/` or `web/assets/css/`. Data responses are cached in memory for 15 minutes. The last successful asset list is written to the `universe` table and used as a fallback when Yahoo and brapi fail. Errors return `{"message": ...}` (400 invalid request or refused action, 403 foreign origin, 404, 405, 500 internal, 502 external source); JSON responses turn NaN/infinity into `null` (`clean`).

API contract (computed results):

- `GET /api/configuracoes` → `{strategy: {target, fraction, targetPct, fractionPct, reversal, kinds: [{group, groupLabel, key, target, fraction, label, text, reversal, targetPct, fractionPct}]}, options, groups, default, ranges}`; `POST /api/configuracoes` with `{target, fraction, kinds: {group: forca|parcial|reversao}}` (in %; target 0.5–500, fraction 1–100; unknown group or rule → 400; missing groups take the default) saves it and returns the same plus `message`. The Carteira analysis cache signature includes the settings; each position follows the rule of its group (`analyze_portfolio(strategy=)` takes a rule or a `(ticker, market) → rule` function).

- `GET /api/scan[?force=1][&liquidez=padrao|10|5|3|2|1]` → the screener scan, with the ranking filtered by the chosen liquidity floor (`screener.LIQUIDITY`: `padrao` = `minAvgVolume`/`minAvgVolumeByKind`, the others R$ N million per session for every type; payloads are built once per choice of liquidity and per-type sell rules, `ScanJob.payload(liquidity, kinds)`, without a new scan). If the saved scan is still valid (`ScanJob._fresh`: younger than `CONFIG["cacheTtlMinutes"]` (60; `browserCacheTtlMinutes` (120) in the browser), or made after the last close (`core.last_close`) while no session is open (`core.in_session_hours`), which is the case of the daily update's scan until the next opening) and `force` is not set: `{state: "done", scan}`. Otherwise it starts one in a background thread (one at a time) and answers `{state: "running", done, total}`; the page polls every 700 ms. On failure: `{state: "error", message, scan}` with the last saved scan (or null); the next call tries again. `scan` = `{timestamp (ms), liquidity, universeSize (assets above the chosen floor + failures), minAvgVolume, topN, failures (count), apiErrors (failures other than "histórico insuficiente"), liveSession, views}`, where `views[mode]` (`fechamento`, `intradiario`) = `{refDate, scanned, rankings}`, where `rankings` has one entry per type in `KINDS` order: `{kind, scanned, minAvgVolume, duplicates (ETFs left out as clones), breadth, regime ("alta"|"misto"|"defensivo", or null with fewer than `regimeMinAssets` (20) assets of the type), loose, strict}`, and `loose`/`strict` = `{qualified, top: [{ticker, name, sector, price, change, setup, bt (`{wins, trades, winRate, avgReturn, open, openReturn, recentTrades, recentWins, recentReturn}`: the asset's backtest with the sell rule of its type — `analysis.backtest` has `loose`/`strict` with the CONFIG partial sale and `looseRev`/`strictRev` with the reversal only, `screener.backtests`/`bt_key`; open buys marked at the last close; recent = closed in the last `recentWindow` (756) sessions), score (with that bt's win rate), pressure (total), bottle ("cheia"|"quase"|"enchendo"), justification: [{label, items}] (Setup, Volume, Momentum, Tendência, Estrutura, each with its signals; shown one line per aspect: bold title, then the signals separated by "·", a signal never broken in the middle; at ≤ 640px the list is hidden and a "Justificativa" `signalBadge` opens it in the floating box, one paragraph per aspect)}], avgPressure, avgWinRate}`. The full scan is also written to the `scan`, `scan_failures` and `scan_analyses` tables (`write_scan`/`read_scan`) and read at startup; bump `SCAN_VERSION` if the shape of the analysis objects changes, and add/remove the column in `database.ANALYSIS_FIELDS`.

API contract (raw data, kept for debugging):

- `GET /api/universe` → `[{ticker, name, sector, kind, close, volume, avg_volume}]` (Yahoo list + brapi sector).
- `GET /api/history/{TICKER}[?market=b3|us|crypto|fx]` → `{ticker, candles: [{date, open, high, low, close, volume, adjustedClose}], dividends: [{date, amount}]}`. Yahoo is asked for `range=10y&interval=1d&events=div`. `dividends` is sorted by date; Yahoo's dividend date is the **ex-date** (first session without the right) and `amount` is per share. The screener ignores `dividends` and `adjustedClose`.
  - `market` picks the Yahoo symbol (`YAHOO_SYMBOL` in `market_data.py`): `b3` (default) → `TICKER.SA`; `us` → `TICKER`; `crypto` → `TICKER-USD`; `fx` → `TICKER=X` (e.g. `USDBRL`). Outside B3 the prices are in the asset's currency (US$). Any other `market` returns 400, and the ticker must still be alphanumeric (so `BRK.B` is not supported). The cache key includes the market (`history:{market}:{TICKER}`).
  - Timestamps: B3 and US candles fall on the session date in São Paulo time, but crypto candles are stamped 00:00 UTC and FX candles 23:00 UTC (midnight in London), which is the *previous* day in São Paulo. `market_data.history` re-stamps them (`restamp_days`, UTC for crypto, Europe/London for FX) to noon São Paulo of the market's own day.
- `GET /api/cdi?from=AAAA-MM-DD` → `{rates: [{date, rate}]}`, the daily CDI in % per day from the Banco Central (SGS series 12). The BCB limits each query to 10 years, so longer ranges are fetched in 3,650-day windows. Cached for 12 hours. A bad `from` returns 400.
- `GET /api/proventos/{TICKER}` → `{ticker, events: [{type, rate, comDate, paymentDate, relatedTo}]}`, the cash dividends announced on B3 (last ~12 months) with data-com and payment date, from B3's public listed-companies API (`sistemaswebb3-listados.b3.com.br/listedCompaniesProxy/CompanyCall/{method}/{base64 JSON}`, no token; brapi's dividends need a paid plan). `GetListedSupplementCompany` with the first 4 letters lists the events per ISIN; for companies, the ticker's ISIN comes from `GetDetail` (`otherCodes`); funds (`codeCVM` "0") use the quota ISIN `BR{base}CTF…` for tickers ending in 11. `type` is B3's label (`DIVIDENDO`, `JRS CAP PROPRIO`, `RENDIMENTO`), `rate` is R$ per share, `paymentDate` is null when not set yet. ETFs and BDRs return `events: []`. Cached for 6 hours.

## Database (`data/` locally, D1 when published)

Locally, the `data/` folder is the application's database: one Parquet file per table, with fixed schemas in `database.SCHEMAS`. In the published version the same tables live in Cloudflare D1: each table is one row of `mp_tables (name, rows, updated_at)` holding the JSON text of its rows, and `backup=True` copies the previous row to `mp_backup` in the same transaction (created by the Worker on first use; no migrations). Row order is meaningful (display order of portfolios, classes, assets and entries). Tables that don't exist yet read as empty. `data/backup/` keeps the previous version of the portfolio tables (written on every action).

- **Portfolios** (linked by `portfolio_id`): `portfolios` (`id`, `name`), `portfolio_classes` (`name`, `target`), `portfolio_assets` (`ticker`, `class`, `market`, `target` nullable), `transactions` (`id`, `date`, `ticker`, `type`, `quantity`, `price`, `fees`, `fx`), `fixed_income` (`id`, `name`, `class`, `target`), `fixed_income_entries` (`item_id`, `id`, `date`, `type`, `amount`) and `portfolio_goals` (`id`, `name`, `kind`, `target`, `withdrawal`, `initial`, `use_portfolio`, `monthly`, `rate`, `inflation`, `adjust`, `target_date`, `created`; `goals` in the document, `GOAL_COLUMNS` in `portfolio_store`). `created` is set when the goal is saved for the first time and kept on edits; `normalize_portfolio` fills it with today for goals saved before it existed. Numbers are `float64`; on read, integral values come back as `int` and null optional fields are omitted, so the document is the same as the old JSON.
- **Saved history** (one table per asset, `history_{market}_{ticker lowercase}`, e.g. `history_b3_petr4`, schema `database.HISTORY_SCHEMA`: `date` (unix), `open`, `high`, `low`, `close`, `volume`, `adj`, `dividend`; candle rows have `dividend` null, dividend rows only `date` + `dividend`; locally in `data/history/`, in D1 shared by every user like the screener tables). `market_data.load_history` reads it and asks Yahoo only for what is missing (`update_range`): saved up to the last closed session (`last_closed_day`: B3/US the last weekday after 18h São Paulo, crypto yesterday UTC, FX the previous weekday in London) and no session open (`live_session`) → nothing; up to date during the session → `LIVE_RANGE` `5d` (the live candle, not saved); behind → the smallest `range` that covers the last saved candle to now plus `HISTORY_OVERLAP_DAYS` (7) (`1mo`, `3mo`, `6mo`, `1y`, `2y`); nothing saved, older, or saved in the old 5-year format (`legacy_history`: first-to-last candle span between `LEGACY_HISTORY_DAYS` (1826) − 10 and + 1 days; an asset with really ~5 years of sessions is re-downloaded only on the few days its span crosses that band) → `FULL_RANGE` `10y`. It merges (`merge_history`, days compared in the market's zone: São Paulo, UTC for crypto, London for FX). Yahoo's `close` is split-adjusted and `adjustedClose` dividend-adjusted, so any event rewrites the past: if the close or adjusted close of a day present in both differs by more than `HISTORY_TOLERANCE` (0.01%), the 10 years are downloaded again. Candles older than `HISTORY_DAYS` (3652) are dropped; only closed sessions (day ≤ `last_closed_day`) are saved, and the table is rewritten only when that part changed (normally once a day, by the daily update). Read/write failures are logged and fall back to the full download.
- **Screener**: `universe` (the last asset list, fallback when Yahoo and brapi fail: `ticker`, `name`, `sector`, `kind`, `close`, `volume`, `avg_volume`; an old list without `kind` counts as stocks), `scan` (one row: `version`, `timestamp`, `universe_size`), `scan_failures` (`ticker`, `reason`) and `scan_analyses` (one row per ticker × mode, with the asset's `kind` and `duplicate_of`, and the nested analysis flattened into the columns of `ANALYSIS_FIELDS`; `ma_name` null = no tested MA, `pressure_total` null = no `pressure`/`backtest`).

## Screener (screener.py + app.js)

1. **`scan_job.status(force, liquidity)`** / **`run_scan`** load the universe and analyze the tickers with `CONFIG["batchSize"]` (8) threads. **Liquidity filter:** the scan analyzes everything down to `scanFloor` (R$ 1 million, the lowest choice) and stores each asset's 20-session `traded` value (column `traded` of `scan_analyses`); the "Liquidez mínima" select of the page (`#liquidity`, remembered in `localStorage` under `LIQUIDITY_KEY`, shared with the Backtest page) picks which assets enter the ranking (`above_floor`, `liquidity_floor(kind, choice)`), so changing it never rescans. The text below describes the default (`padrao`). The universe is a **liquidity floor**, not a fixed count: `load_universe` keeps the listed assets of the `KINDS` types (`acoes`, `fundos`, `etfs`, `bdrs`; ~320 candidates) whose 3-month mean traded value (close × `avg_volume` from the Yahoo list) is at least `prefilterRatio` (60%) of `scanFloor`, only to skip downloading illiquid ones; then `analyze_ticker` computes the mean traded value of the last `liquidityWindow` (20) **closed** sessions (`avg_traded_value`, without the live candle) from the history the scan already downloads and returns `None` (dropped, not a failure) when it is below `scanFloor`; the default view keeps the assets above the type's floor (`min_avg_volume`: `minAvgVolume` R$ 5 million, `minAvgVolumeByKind` R$ 3 million for `fundos`). Per type (as recommended by the financial analyst): `fundos` (`adjustDividends`) are analyzed on dividend-adjusted candles (`core.adjusted_candles`: o, h, l, c × adj / c; the last candle is unchanged), because the monthly ex-date drop would tilt the MM200 down and fire the exit rule (HGLG11: 34 exits in 5 years raw against 15 adjusted); liquidity is always measured on the raw close; an ETF whose mean daily range over `etfRangeWindow` (250) is below `etfMinRange` (0.3%) is fixed income and dropped; `bdrs` use `pressureWeights["bdrs"]` (no Volume component: on B3 it is market-maker flow); and `build_scan` calls `mark_duplicates`: from the most to the least traded, an ETF whose daily returns over `etfCorrelationWindow` (120) correlate ≥ `etfDuplicateCorrelation` (0.98) with a kept one gets `duplicateOf` and stays out of the ranking (BOVV11, BOVX11… → BOVA11). The 20-session mean keeps a stock in the universe after a single weak day. Each ticker above the floor needs at least `minCandles` (261) candles, otherwise it goes to `failures` as "histórico insuficiente".
   - Each ticker is analyzed twice and stored as `{ fechamento, intradiario }` (`analyze_ticker`). Yahoo's last daily candle is the live, unfinished session while B3 is open. `session_in_progress` checks whether that candle is from today in São Paulo time and the clock is before `SESSION_END_HOUR` (18). If so, the `fechamento` analysis drops that candle. `views` prepares both bases × with/without candle filter, so the "Base" selector and the "Exigir candle de rejeição" checkbox only switch views in the page (no refetch); the base choice is saved in `localStorage` under `MODE_KEY`.
2. **`market_data.history`** uses raw OHLC. Yahoo's `close` is already adjusted for splits but not for dividends, which matches TradingView's default chart, the user's reference. Do not apply `adjustedClose`: dividend adjustment lowers past prices and inflates the MM200 trend. For example, it made CMIG4 look like an uptrend while TradingView showed MM20 and MM50 below MM200.
3. **`evaluate_setup(ind, i, confirm_previous)`** (in `core.py`, because the Carteira's "pullback" contribution mode uses it too) applies the hard filters:
   - MM200 is above its value from 20 sessions ago, and the close, MM20 and MM50 are all above MM200. MM20 below MM50 is allowed.
   - The pullback depth is measured from the 20-day high to the lowest low since that high, not to the current close, so a rebound that has already started still counts. It must be at least `minPullback`.
   - The current close must be between 0 and `maxDistance` (3%) above the tested MA. In intraday mode (`confirm_previous`, used only while a session is in progress), the last closed session must also be above it. Earlier closes in the pullback may sit below the MA, but no more than `maxBelowDistance` (3%) below that day's MA value. Deeper closes mean the support was lost, not tested (BBSE3 at −3.7%, INTB3 at −6.2%). The closest MA that passes among MM20, MM50 and MM200 becomes the "Média Testada". The backtest always uses the single-candle rule.
   - `okStrict` also requires a rejection candle (doji, martelo or corpo estreito). The "Exigir candle de rejeição" checkbox switches between the `loose` and `strict` views. It is unchecked by default: in the backtests of the user's strategy the candle filter did not help.
4. **`pressure(ind, i, setup, live)`** measures the "gas" accumulated in the pullback since the 20-day high (`setup["topIdx"]`). It combines four 0–100 components and describes the pattern; it is not a win probability. `live` is the same flag passed as `confirm_previous`; when true, the volume parts use `e = i − 1` to skip the partial volume of the session in progress. `compute_indicators` provides `atr14` (Wilder) for the ATR-based parts.
   - Volume (25%) = 0.4·A + 0.3·B + 0.3·C. A: OBV-versus-price divergence, `clamp01(0.5 + obvPct − closePct)` over 60 days. B: mean volume of up days in the 20 sessions up to the high ÷ mean volume of the 60 sessions up to the high, mapped from 0.9 to 1.3. C: volume dry-up, mean volume after the high ÷ mean volume of the 20 sessions up to the high, mapped from 1.2 down to 0.7 (0.5 when there is no pullback candle yet).
   - Momentum (30%) = 0.4·regime + 0.3·reset + 0.3·stochReset, plus +15 for a hidden bullish divergence (higher low with a lower RSI than the 30 sessions before the high), capped at 100. regime: lowest RSI since the high, mapped from 30 to 40. reset: RSI drop from the high to now, over 15 points. stochReset: lowest Stochastic since the high, mapped from 50 down to 20. Oversold is not rewarded, and the classic divergence was removed.
   - Trend (25%) = 0.35·hist + 0.35·zero + 0.30·support. hist: share of the pullback's most negative MACD histogram already recovered (1 if it never went negative). zero: MACD ÷ ATR14, 1 at or above zero and 0 at −0.5 ATR. support: `1 − ma.dist / maxDistance`.
   - Structure (20%) = 0.6·(1 − Bollinger bandwidth percentile over 120 days) + 0.4·compression, where compression maps the 5-session high-low range from 4 ATR down to 2 ATR. There is no candle bonus, since `okStrict` already filters by candle.
5. **Exit rules.** `exit_signal(ind, i)` is the user's sell rule ("regra B"): the close is below MM20, MM50 and MM200 **and** the downtrend is formed (MM50 < MM200). On top of it, each buy (lot) sells `EXIT["partialFraction"]` (50%) when a later candle's high reaches `EXIT["partialTarget"]` (+10%) over that buy (`core.EXIT`, merged into `CONFIG`); the rest of every lot leaves on rule B. The partial has two timings (`core.PARTIAL_TIMINGS`, the `parcial`/`forca` rules of Configurações): `alvo` sells when the high touches the target; `forca` waits, after the target is touched, for the first close still at or above it with the rally without strength (`core.weak_close`: less than 1 ATR above the MM20 or RSI below 65) and sells at the next open — unless rule B fires first. The partial doesn't change the buys or the rule-B exit, so `backtest_lots` computes the lots once and `with_partials(ind, lots, target, timing)` adds the partial; `backtests` keeps six summaries (`loose`/`strict` with the partial at the target, `…Forca` with it by strength, `…Rev` with the reversal only; columns `bt_loose_forca_*`/`bt_strict_forca_*`, `SCAN_VERSION` 9) and `bt_key` picks one by the group's rule (`BT_SUFFIX`). In the portfolio backtests (60/40, 2017–2026, with income tax) `forca` was the best exit for stocks; the partial at the target only beat rule B alone by ~1 p.p./year. There is no stop loss in the app.
6. **`backtest(ind, strict)`** replays that strategy over the asset's own history (10 years). From candle 220 on, an `evaluate_setup` signal (`ok`, or `okStrict` when strict) buys at the **open of the next candle**. Like the user, it **buys again on every new pullback** while the position is open, but never twice in the same pullback: a new buy needs its price at least `reentryDistance` (5%) away from every buy of the open position (the user's "fora da região onde já aportei"; on UGPA3 this reproduces the six buys he marked from Dec/2025 to Oct/2026). `backtest_lots` returns each lot (`entry`, `partial`, `exit`: candle index and price): the partial fills at the target price, or at the open when the candle already opens above it, and only from the candle after the buy candle. When `exit_signal` fires on a close, the rest of all the buys is sold at the next open. `backtest` summarizes it: each buy is one trade, its return is `fraction × partial + (1 − fraction) × exit` (`lot_return`), and a win is a positive return. Buys still open at the end of the history don't count. It returns `{ wins, trades, winRate, avgReturn }`: the win rate is smoothed toward `priorWinRate` (0.5, neutral) with `priorWeight` pseudo-trades, and `avgReturn` is the mean return per closed buy in %. The ranking and the Carteira still show the setup every day it holds; the same-pullback rule exists only in the backtest. `evaluate_setup` serves both the live signal and the backtest, so changes to it affect both.
7. **`build_ranking`** computes `score = pressure * 0.6 + winRate * 0.4` and sorts by it; `views` keeps the top `topN` (20) with `bottle_state` (≥ 75 cheia, ≥ 60 quase cheia) and `justification` (the text of the last column), and, per type, the `regime` from the breadth (≥ 60% alta, ≥ 40% misto, else defensivo). `render` in `app.js` fills the KPIs (totals and per-type counts) and one panel per type (`renderRankings`/`rankingPanel`: title, scanned/qualified/averages, regime and the table). If fewer than 20 assets of a type qualify, its panel shows fewer rows and a note. It never pads the list.

Each ranking row also has `advice` (`screener.advice`, added per request by `api.scan_with_advice`, not cached: `/api/scan` takes `carteira=` = the portfolio last opened in Carteira, else the first): `COMPRAR` or `AGUARDAR` with the reason, never a sell (selling belongs to the Carteira). AGUARDAR when the portfolio has an open buy within `REENTRY_DISTANCE` (5%, `core`) of the price, or, outside `adviceIgnoreKinds` (the `internacionais` group), when the trend is weak (`weak_trend`: MM200 up less than `weakSlope` (1%) in 20 sessions, negative 12-month return, or the pullback reached the MM200; analyses carry `mm200Slope`, `return12m` and `return6m`, also in the ranking rows) or the asset returned less than BOVA11 over `relativeWindow` (126) sessions (`weak_relative`: `return6m` < the row's `benchmark6m`, BOVA11's `return6m` in the same scan and base, `RELATIVE_BENCHMARK`). The weak-trend and relative-strength checks live in `core` (`ENTRY`, `entry_stats`, `entry_warnings`) and are shared with the Carteira: a position in the setup only gets the Situação COMPRAR (and is only eligible in the aporte's pullback mode) when they pass, outside the `internacionais` group and outside B3 (`holding_signal`/`setup_now` with `check_entry` and BOVA11's 6-month return, `bench6m`); otherwise MANTER with the reason / "Pullback em tendência fraca". COMPRAR gets `priority: True` and a reason starting with "Prioridade" (same "COMPRAR" badge) when the row is in the type's Top `priorityRank` (5) or has Score ≥ `priorityScore` (65) (`is_priority`; `with_advice` passes the rank), suggesting up to `prioritySize` (1.5) × the normal buy. This is the rule set "E" of the backtests of Oct/2026: per buy, weak trend, weaker than BOVA11 and outside the priority all returned less in both halves of 2017–2026; in total portfolio profit no rule set beat random draws (path dependence: a few big winners decide), so the indication improves the average buy, not a proven total return. The pressure stays only inside the Score: on its own it did not predict better buys. In the portfolio backtests (stocks, 2017–2026) weak-trend buys returned less in both halves of the period (−2.1% x +0.8%, −0.6% x +1.4%); for international assets no condition justified waiting. The asset's history never makes AGUARDAR (in the portfolio backtests, skipping stocks with a negative 10-year or 3-year history cut the profit, R$ 307 k without a filter x R$ 243–261 k with one); when the recent (3-year) backtest lost money with ≥ `adviceMinTrades` (2) closed buys, outside `adviceIgnoreKinds` (BDRs, where history predicted nothing), COMPRAR's reason gets an "Atenção" line (`recent_negative`). COMPRAR's reason states the exit plan of the rule of the asset's type (`with_advice(payload, lots, strategy_for)`, `advice(a, lots, strategy, kind)`).

The ranking table has 10 columns (the "Estado da Garrafa" badge sits under the pressure %, in the same cell, since it is only the pressure in bands; Indicação before Justificativa, then "Análise IA" with the "ANALISAR ATIVO" button: `copyAnalysis` in `app.js` asks `/api/scan/prompt` and copies it through a `ClipboardItem` holding the promise, so Safari keeps the click gesture; if the browser refuses, the text opens in a `dialog.copy-dialog` to copy by hand) (no stop loss, take profit or potential gain). The "Histórico (backtest)" cell (`btCell`) shows the win rate, `wins/trades` and the mean return per closed buy, then the last 3 years (`recentWins/recentTrades` and mean) and the open buys (count and mean at today's price). If you add or remove a column, update the `<thead>` in `rankingPanel`, the row template in `tableRows` and the `colspan="10"` there (all in `app.js`).

8. **BOVA11 KPI** in the macro panel: `bova_kpi(mode)` computes the price change over the last `bovaLookback` (252) sessions and whether the close is above or below the three MAs (on the "fechamento" base without the live candle); `renderBova` shows it, or "—" on failure.

The old "Minha carteira" panel of the screener was replaced by the Carteira tab; its Manter/Atenção/Vender rule now lives in the positions table there.

## Backtest page (backtest.html + backtest.js; screener.backtest_view, portfolio_backtest)

Two modes (`#btMode`, "Um ativo" / "Carteira"; fields marked `data-mode`). **Carteira** simulates real life: one cash that follows the screener ranking day by day, starting with the initial capital (plus monthly contributions on the first session of each month). Each session the ranking is rebuilt as the screener would have shown it that day (liquidity of the time, setup, Score with the past only, top N per type) from every asset in the saved B3 list, and its assets buy at the next open with `position` % of that day's equity, highest Score first, while there is cash for at least half of it. Re-buys follow `reentryDistance` and at most `maxAssets` different assets are held. Partial sales and rule-B exits return the money to the cash, which pays the next buys; dividends enter on the ex-date; idle cash earns the CDI (rate of day d on the next session; optional); every buy and sell pays `cost`. The same run with rule B alone, BOVA11 (adjusted close) and the CDI with the same flows are the comparison (`strategies`; the chart shows profit = equity − contributed). Delisted companies are not on Yahoo, so some survivorship bias remains (stated in the footnote). The page shows the summary cards of the chosen rule (plus the "Só a regra B" line), the "Ano a ano" table (`_yearly`: per calendar year, profit in R$ = end − start − contributions of the year, and the return by quota, which ignores the contributions; first and last years may be partial), the comparison table, "Operações no gráfico" (pick an asset: candles/MAs from `GET /api/backtest` for it in the same period, markers from `markers[ticker]`; clicking a trade row focuses `trade.range`) and the trades table (rank and Score of the signal day, sessions). Both the trades table and the "Um ativo" lots table are paginated in the page (`PAGERS`, `setupPagers`, `pageRows`: 25/50/100 rows per page, the same for both and remembered in `marketpressure_backtest_por_pagina`; the pager is hidden up to 25 rows). "Testar robustez" (`#pfRobustBtn` + `#pfRobustWindow`, `runRobustness`/`renderRobustness`/`renderRobustChart`, panel `#pfRobust`) runs the same form in each period and shows the verdict, KPI cards (median IRR and range, median p.p. over BOVA11, scoreboard bars, worst/median drawdown, median profit over contributions), the summary, a Chart.js 4.4.1 grouped bar chart of each line's IRR per period and the table (profit of each line with ✓/✗, buys, partial − rule B in R$, IRR, BOVA11 IRR, difference in p.p., max drawdown). Each result (Um ativo, Carteira, robustez) has an "ANALISAR BACKTEST" button (`#btAnalyzeBtn`, `#pfAnalyzeBtn`, `#pfRobustAnalyzeBtn`, `analyzeResult` → `copyServerText`) that copies the `backtest_prompt` text. The first run downloads and analyzes hundreds of histories (~40 s locally, saved afterwards; signals cached in memory); in the published version it runs in Pyodide and is slower.

**Um ativo**:

The same `backtest_lots` drawn lot by lot for one asset (closed sessions only; funds on dividend-adjusted candles, like the screener; `us` market in US$). The page can change the partial target and fraction (0 = rule B only) and require the rejection candle; the summary always compares with rule B alone (`onlyB`). Stats: lots (closed/open), raw and smoothed win rate, mean/median/best/worst closed lot, sum of all lots in % of one lot (open lots marked at the last close), partial hits, mean days, mean giveback from the highest close to the exit, mean maximum gain, and buy-and-hold from the first buy. No costs, taxes or dividends.

## Carteira (carteira.html + carteira.js; portfolio.py + portfolio_service.py + portfolio_store.py)

Portfolios are stored on the server in the database tables in `data/` (never in `localStorage`; the browser only remembers the last selected portfolio under `marketpressure_carteira_atual`). Every change is an action sent to `POST /api/carteira/acao` (`act` in `carteira.js`); the server validates, writes and returns the new document, and only then the page redraws (`refresh`). Ids come from `uuid.uuid4()` on the server.

`refresh()` fetches `/estrutura` (selectors, class table, history: works with no entries), then `/analise` (everything with quotes) and, in parallel, `/proventos` (filled last). Responses that arrive after a newer refresh/aporte/typing are discarded by sequence counters (`state.run`, `aporteSeq`, `txSeq`, `batchSeq`).

**Page layout (sub-tabs).** The site tab bar and the portfolio selector panel (new, rename, delete, refresh, and "ANALISAR CARTEIRA" (`#analyzePortfolioBtn`, `data-needs-entries`): `analyzePortfolio` copies `GET /api/carteira/{id}/prompt` with `copyServerText`) stay at the top. Below them, a sub-tab bar (`#subtabs`, WAI-ARIA tabs: `role="tablist"`, buttons `#tab-{name}` with `aria-selected`/`aria-controls` and a roving `tabindex`, sections `#panel-{name}` with `role="tabpanel"`/`aria-labelledby`) shows one section and hides the others with `hidden`:

1. **Visão geral** (`visao`, default): Resumo (KPIs) → Evolução do patrimônio (`renderPatrimony`: stacked bars, Investidor10 style, with the mode buttons `#patrimonyModes` ("Aplicado e ganho" | "Por classe": each class's value stacked, colors `CLASS_COLORS`, the class select disabled), a class select `#patrimonyClass`, period buttons `#patrimonyPeriods`, the period summary above the chart (`renderPatrimonySummary`: end value, net contributions, valorização, and per class in the class mode) and a tooltip with the gain % and the bar's net contributions) → Rentabilidade acumulada (chart) → Alocação por classe, read-only (`#allocationViewBody`, 7 columns, with an "Editar classes e metas" link to `#configuracoes`) → Posições → Metodologia note.
2. **Aportes e lançamentos** (`aportes`): the Aporte calculator (see below), which can be collapsed with the "Recolher/Expandir" button (`#aporteToggle`, `aria-expanded`, remembered in `localStorage` under `marketpressure_aporte_recolhido`) → Nova operação → Renda fixa → Histórico de lançamentos (the `HISTORY_LIMIT` = 10 most recent, with a "Ver todos (N)" / "Ver menos" button). After a save, the form message shows the server's confirmation ("Compra de 100 PETR4 registrada.") with a "Ver na visão geral" link (`setSavedMsg`); the tab never changes by itself.
3. **Proventos** (`proventos`): Proventos a receber → Proventos recebidos.
4. **Metas** (`metas`): the goal form (name, kind `renda`|`patrimonio`, target or monthly income, withdrawal % a year, initial value or "Partir do patrimônio atual", monthly contribution, expected return and inflation % a year, optional target date, "Corrigir o aporte pela inflação") with "Salvar meta" (`salvar_meta`, also edits with `goalId`) and "Simular sem salvar" (`/metas/simular`), then one card per goal (`goalCard`: summary, progress, KPIs, milestones 25/50/75/100%, Chart.js projection, scenarios ±2 p.p. × contribution ×1/1.5/2, year-by-year table in `<details>`; "Editar"/"Excluir" → `excluir_meta`). Goals with "Partir do patrimônio atual" are refreshed from the portfolio (value with today's quotes) every time the sub-tab loads and also show "Realizado × planejado" (`result.tracking`: the plan starts at the portfolio value on `created` and follows the goal's contribution and return in nominal terms, the current month's contribution pro-rated; KPIs, summary and a Chart.js line chart) and "Previsão pelo plano e pelos dados reais da carteira" (`result.projections`). Loaded by `loadGoals` when the sub-tab is shown (`state.goals` is reset on every refresh). The projection is monthly in today's money (`goals.py`); the analysis cache signature ignores `goals`, so editing a goal doesn't reload quotes.
5. **Configurações** (`configuracoes`): "Classes e metas" (`#allocationBody`, 4 columns: the fixed class name, editable target, the class's assets/titles and its sell rule from Configurações (`/estrutura` `classes[].rule`); sum ≠ 100% warning; Mover ativo; rendered from `/estrutura` by `renderClassConfig`, so it works before the first entry) and "Meta por ativo" (`#assetTargetsBody`, from `analise.assetTargets`, with the same per-asset target field as the Aporte table, `targetField`, both saved by `onAporteTableChange` through the `meta_ativo` action).

The active sub-tab lives in the URL hash (`#visao`, `#aportes`, `#proventos`, `#metas`, `#configuracoes`), so reload and back/forward keep it (`goTab` sets the hash, `hashchange` calls `showTab`); without a valid hash the last one is read from `localStorage` (`marketpressure_carteira_aba`), else `visao`. The old sub-tabs "Aportar" and "Lançamentos" were merged: `#aportar` and `#lancamentos` (and those values saved in `localStorage`) open `aportes` (`TAB_ALIASES`/`resolveTab`), and `#lancamentos` also scrolls to "Nova operação". Left/right arrows (circular), Home and End move between sub-tabs. No element may have an id equal to a tab name (the hash would scroll to it). `showTab` calls `chart.resize()`/`update('none')` when Visão geral is shown, because a chart drawn while hidden has zero size. Empty states: with no portfolio only `#emptyState` shows (sub-tabs hidden); with a portfolio but no entries (`estrutura.hasEntries`), elements marked `data-needs-entries` are hidden and those marked `data-no-entries` are shown (the Visão geral callout with "Lançar primeira operação", which opens "Aportes e lançamentos" with the focus on the ticker field, and short notes in the calculator and Proventos).

- **Classes are fixed** (`portfolio.CLASSES`, in this order: Ações, Fundos imobiliários, ETFs Brasil, Internacionais — BDRs, ETFs from abroad, US and crypto — and Renda fixa) and are the same groups as the sell strategy in the site's Configurações tab (`CLASSES[].group` → `strategy.GROUPS`; Renda fixa has no rule). The "Situação" of a position follows the rule of the asset's class (`strategy.asset_rules(settings, {ticker: class})`). A new portfolio starts with the ARCA targets (`DEFAULT_TARGETS`: Ações 35, Fundos imobiliários 20, ETFs Brasil 0, Internacionais 35, Renda fixa 10). The user only edits each class target (`meta_classe`) and moves an asset or title to another class (`mover_ativo`); `renomear_classe`, `nova_classe` and `remover_classe` are refused (`fixed_classes`).
- **Migration** (`normalize_portfolio`/`normalize_doc`, applied on every read): free class names of before map to a fixed class by name (`CLASS_ALIASES`: "renda fixa", "internac/exterior/global/BDR/cripto", "FII/fundo/imobili", "ETF", "Ações"); an asset whose old class doesn't map goes to the class of its type by code (`suggest_class`), a title to Renda fixa; each fixed class target is the sum of the old targets that map to it (by name or, without a match, by where most of the old class's assets went). The oldest format (`targets` with Ações, ETFs, FIIs, BDRs, Renda fixa) goes through the same mapping. It is idempotent, and `write_doc` normalizes before writing, so the tables always hold the current format (`version: 2`).
- **Markets**: `assets[T].market` is `b3` (missing = b3), `us` or `crypto`, chosen when the asset is first added. For a new ticker the server suggests a class (`portfolio_service.suggested_class` → `suggest_class(ticker, market, kind=, international=)`): outside B3, BDRs and ETFs from abroad (`market_data.international_etf`, by the name) → Internacionais; on B3 the screener type from the `universe` table (ações, fundos, etfs → ETFs Brasil) or, without it, the code (final 32/33/34/35/39 → Internacionais, 11 → Fundos imobiliários, otherwise Ações). Price and fees of a transaction are typed in the asset's currency (US$ outside B3), prefilled with that day's close; the form also shows a "Câmbio (R$ por US$)" field prefilled with that day's USDBRL close (editable), saved as `fx` (1 on B3). Fractional quantities are accepted on every market. `nova_operacao` also refuses a ticker without Yahoo history.
- `type` is `compra`/`venda` for transactions and `aporte`/`resgate`/`valor_atual` for fixed income. When a ticker, market or date is typed (`onTxInputChange`), the page asks `/ativo` (normalized ticker, new or known, market, suggested class) and `/cotacao` (close of that day or the previous session, and USDBRL), and the price field stays editable.

`portfolio.py` keeps the pure calculations (no network or disk); `portfolio_service.py` loads the data and calls them. `analyze_portfolio(portfolio, histories, cdi_rates, as_of, now)` returns everything the page renders; `analysis_payload` trims it for the page. `histories` holds each ticker's history in its own currency, `BOVA11` and, when there is any non-B3 asset, `USDBRL` (`load_histories`, in parallel).

- **Currency conversion** (`convert_history`): every non-B3 history is converted to reais before anything else: each candle × the USDBRL close of that day (or the last one before it), dividends × the USDBRL of the ex-date. All money values (cost, value, profit, dividends, series) are in BRL. `tx_flow` = (qty × price ± fees) × `fx`. US dividends are gross (the 30% US withholding is not deducted; the page says so). The setup and the Situação use the asset's original (US$) candles.
- **Positions** (`build_positions`, transactions in date order; on the same day buys come before sells): a buy adds quantity and cost (price × qty + fees); a sell reduces the position at the average price and books realized profit = price × qty − fees − average price × qty. `check_sequence` rejects any sell larger than the quantity held on its date (also used when deleting a buy). Position profit = value + sales + dividends − total bought, and return % is over total bought. Deleting the last entry of a ticker also removes it from `assets`.
- **Dividends** (`dividends_received`): for each Yahoo event (ex-date d), quantity held at the end of the session before d (transactions dated < d) × amount per share. The table shows the data-com (the previous session), newest first (ties by ticker). Values are gross estimates (JCP has 15% withholding tax).
- **Dividends to receive** (`dividends_to_receive`/`receivables`, B3 tickers only, from `market_data.proventos`): events not yet paid (payment date today or later, or not set). Data-com before today = "Confirmado", quantity held at the data-com (`quantity_at`); data-com today or later = "Previsto", current quantity. The card (8 columns, `colspan="8"` in `renderReceivables`) is filled after the rest of the page, sorted by payment date ("A definir" last), with gross and net totals (JCP − `JCP_TAX`). It doesn't feed the KPIs or the series: confirmed items already count in "recebidos" by ex-date.
- **Fixed income** (`fixed_income_value_at`): the last `valor_atual` up to the date plus later contributions minus redemptions; before the first update, the net contributed amount. The value only changes when the user updates it, so the return jumps on update days.
- **Daily series** (`build_series`): from the session of the first entry, on the calendar of BOVA11 sessions merged with the portfolio's **B3** tickers' sessions (US and crypto days don't add sessions; on each B3 session they use their last BRL price up to that date, so crypto weekends are folded into Monday) (Yahoo sometimes omits a BOVA11 candle, e.g. 2026-10-07; BOVA11 repeats its last value then). Value = Σ qty × raw close (the same `close` as the screener, forward-filled) + fixed income. Time-weighted return: r_t = (V_t + D_t − F_t) / V_{t−1} − 1, where D_t is the dividends with ex-date t and F_t the net flows (buys and contributions positive; sells and redemptions negative); with no value on the previous day, r_t = (V_t + D_t) / F_t − 1. Accumulated = Π(1 + r_t) − 1. Events on non-trading days go to the next session. BOVA11 uses `adjustedClose` (`adj`), and CDI the product of (1 + rate/100), where the rate of day d accrues to the next session. Transactions older than the 10 years of history enter at the price typed by the user, and the series starts at the first available session (`chart.truncated`, shown on the page).
- **Evolução do patrimônio** (`patrimony_bars`): `build_series` also keeps, per class and day, the value, the cost and the net flows (`series["classes"]`; the flows of a truncated start count here, so the gain is measured from what was paid; average cost of the open positions, as in `build_positions`, plus the net contributed to fixed income, `fixed_income_invested_at`); the bars take the last session of each month (`month_ends`; the current month uses the latest day). Ganho de capital = value − invested (dividends and realized profit don't enter). Each bar is stacked as `base` = min(value, invested), `up` = gain ≥ 0 and `down` = the invested part lost; colors aplicado `#3987e5`, ganho `#199e70`, perda `#d95926`. Periods `PATRIMONY_PERIODS`: 30D (`PATRIMONY_DAILY`: one bar per session of the last `PATRIMONY_DAYS` calendar days), 1A, 2A, 5A, 10A, Tudo (12/24/60/120 monthly bars/all).
- **Periods**: `rebase_series`/`window_returns`/`period_start` restart all three series at 0% at the period start (6M, 1A, 2A, Tudo; 12 calendar months for the KPI, while the screener's BOVA11 KPI uses 252 sessions). The server sends every period ready (`chart.periods`), so the period buttons only switch data. The chart (Chart.js 4.4.1 from cdnjs) has fixed colors Carteira `#3987e5`, CDI `#d95926`, BOVA11 `#199e70` (validated on `#161b22`), one Y axis in %, 2px lines without points and an index tooltip with a vertical crosshair.
- **Situação** (indication) of each open position: `holding_signal` → `position_signal`, following the saved strategy (`strategy.py`), always with `statusReason` (the why, in short paragraphs separated by `\n`, like the Screener's `advice.reason`; the tooltip box shows one `<p>` per line) and `statusKey`. Labels are only COMPRAR, VENDER and MANTER: `sell` "VENDER" when `exit_signal` is true on the closed candles (`closed_for`; crypto closes at midnight UTC), sell everything; `partial` "VENDER 50%" when buys hit the strategy's target and their part isn't sold — with the `forca` rule only once a closed session after the hit closed at or above the target without strength (`open_lots(..., timing, ind)`: `hitDate` = target touched, `dueDate` = when the partial is due, the same day for `alvo`; a buy with `hitDate` but no `dueDate` has `waiting` > 0 and gets MANTER with "fica para a abertura seguinte ao primeiro fechamento em que a alta perder força" and today's RSI/ATR; the VENDER 50% reason says the sale is at the open) (with the `parcial` rule, the reason also tells whether the rally is still strong — `core.trend_strength`: close ≥ `STRENGTH["atrAboveMm20"]` (1) ATR above the MM20 and RSI ≥ 65 — and, if so, that waiting for the rally to lose strength (the `forca` rule) returned more in the portfolio backtests; the position carries `statusStrength`, which the "Analisar carteira" prompt shows as "Força da alta" with a rule in `DECIDE`; information only, the signal doesn't change) (`open_lots`: a buy hits on the first session after its date whose high reaches +target, in the asset's currency; each sale first settles pending partials, the rest comes out of the oldest buys), with `partial: {quantity, lots, due, ...}`; on B3 the quantity is floored, and when it floors to 0 (e.g. a 1-share position) there is no partial: MANTER with that reason; `buy` "COMPRAR" when the asset is in the setup on the last closed session at ≥ `REENTRY_DISTANCE` from every open buy; MANTER otherwise (`attention` when the close is below MM200 without the reversal, `hold` else; the reason gives the next target). With the `reversao` strategy there is no partial. The page maps `statusKey` to a badge (`STATUS_BADGE`).
- **Allocation** (`class_allocation`): value and % per class in the order of `classes`; fixed-income titles count in their own class.
- **Per-asset target** (`asset_targets`): by default each class target is split equally among the class's holdings (assets with quantity > 0 and titles with value > 0). A fixed target (`assets[T].target` or `fixedIncome[i].target`, in % of the whole portfolio, typed in the Aporte table or in Configurações → Meta por ativo; empty = automatic) is kept and the others share the rest. Warnings when fixed targets exceed the class target (the others get 0%) or, with every asset fixed, fall short of it.
- The portfolio value uses the latest candle (intraday during the session) and the header shows "atualizado em DD/MM HH:MM". "Atualizar cotações" asks for a new analysis (the server still caches quotes for 15 min, CDI for 12 h and announced dividends for 6 h).

The positions table has 11 columns (`colspan="11"` in `renderPositions`); fixed-income rows come last. At ≤ 640px its first column (Ativo) stays fixed while the table scrolls sideways (`table.sticky-first` in `styles.css`; `table.sticky-two` fixes the first two, the first at the width `--sticky-w`). Also used by the Screener rankings (`sticky-two rank-merge`: on the phone the Rank column is hidden and the medal + position show above the ticker, `.rank-inline` in `tableRows`), the read-only allocation table, the Aporte calculator's class summary and asset table (`sticky-two`: Escolher + Ativo, `--sticky-w` 0 outside the "escolher" mode; a full-width `td[colspan]` is never sticky, its text goes in a `span.sticky-label`, and the class total row has no colspan), the goal's year-by-year table, and the Backtest's Ano a ano, Comparação and trades tables (trades: `sticky-two rank-merge`, the "#" above the ticker on the phone). The read-only allocation table (Visão geral) has 7 columns and the class table in Configurações has 4 (the last is the sell rule).

### Aporte panel (sub-tab "Aportes e lançamentos")

A contribution calculator following the user's ARCA spreadsheet. Inputs: "Valor que irá investir" (R$), the mode and, in pullback mode, the Base (the screener's `MODE_KEY`). Amount, mode and the chosen assets are remembered per portfolio in `localStorage` (`marketpressure_aporte_{id}`); targets are saved in the portfolio. The page sends the fields to `POST /api/carteira/{id}/aporte` (the amount after a 250 ms pause in typing) and draws the plan. Functions in `portfolio.py`: `contribution_items(portfolio, analysis, mode)` builds the rows (holdings with their per-asset target, BRL price, `sell` and the setup for the base) and `contribution_plan(classes, items, total, amount, mode, selected)` computes:

- Estimated value = portfolio + contribution. For each class and asset: balance, % now, % target, **ideal = estimated × target** and **"a investir" = ideal − balance** (may be negative). With the spreadsheet's test case (portfolio 26,012.78 + 2,000) these match to the cent.
- **Eligibility**: `todos` = every holding; `escolher` = the ticked ones (checkbox column, visible only in this mode); `pullback` = holdings with `evaluate_setup(...)["ok"]` now (`setup_now`: on the "fechamento" base the live candle is dropped; on "intradiario" the live candle is used with `confirm_previous`; fewer than 220 candles = not in setup) plus fixed income, which stays eligible by its target. In every mode, an asset whose Situação is **Vender** (`exit_signal`) gets nothing and the reason is shown.
- **Suggestion** (buy only): the amount is split among the eligible rows proportionally to their positive gap to the ideal; if every eligible row is already at or above its ideal, proportionally to their targets (`distribute`). `split_cents` uses the largest-remainder method, so the parts sum exactly to the amount. No eligible row → "Aguardar" with an explanation.
- **Redirected**: what the excluded (non-"Vender") rows would get in mode `todos` is reported per class and shown on each of them ("receberia R$ X no modo todos"); in pullback mode they are labeled "Aguardar pullback".
- **Shares**: floor(suggestion ÷ BRL price), whole shares on B3 and 4 decimals for US and crypto; the effective value and the leftover are shown per row, per class and in total.
- **Situação** column: status key `setup` "Em pullback (MMxx)", `wait` "Aguardar pullback", `sell` "Vender" or `fixed` "Renda fixa" (badge chosen in the page by `PLAN_BADGE`). The asset table (11 columns, `colspan="11"`) is grouped by class (members sorted by value) with a total row; the class summary above it has a double bar (`allocBar`, reusing `.alloc-bar`): top = % now, bottom = % after the suggestion, tick = target.
- **Registrar compras sugeridas** (`#aporteRegisterBtn`, shown when `plan.canRegister`: not "Aguardar" and at least one eligible quoted asset with shares > 0). It opens a review list below the calculator (`#batchPanel`, no `prompt`) with the plan's `batchRows` (`batch_rows(plan, analysis["open"], date)`): one row per eligible asset with shares > 0: include checkbox, date (today in São Paulo; a date field on top applies to every row, and each row can still change it), quantity = suggested shares, price = current price in the asset's currency, câmbio = the day's USDBRL (US and crypto only), fees 0, and the total in R$. Fixed-income titles with a suggestion > 0 become an `aporte` entry with that amount. The page keeps what is typed as text and asks `POST /api/lote/totais` for the totals (only the totals change, so the focus stays in the field). "Confirmar lançamentos" sends the `registrar_lote` action: the server validates every included row with `validate_transaction` / `validate_fixed_income_entry` (the same rules as the single forms); if any row fails, `rowErrors` comes back, the error is shown on that row and nothing is saved. Otherwise every row is written in **one** save (all or nothing), an asset missing from `assets` gets the class and market of its position, the list closes, the calculator recalculates and `#aporteMsg` shows the server's confirmation ("5 compras e 1 aporte registrados.", with "Ver na visão geral"). Changing the amount, mode, base, choices or targets closes an open list, because it was built from the previous plan. The state lives in `state.batch` (`{ date, amount, rows }`).

## Testing without a browser

- **Automated tests**: `python -m unittest discover -s tests -t .` (from the project root; offline, ~2 s). `tests/support.py` has `DatabaseTestCase` (each test gets an empty database in a temporary folder and synthetic quotes in place of `market_data.raw_history`) and `candles()` (uptrend with waves, which produces setup signals). `test_core`, `test_portfolio` (pure calculations), `test_market_data` (saved history: `FakeYahoo` answers each `range`; incremental fetch, split → full download, D1), `test_screener`, `test_store` (actions, goals), `test_goals` (goal validation and projection), `test_portfolio_backtest` (shared cash: final equity = initial + every trade's profit, same flows for the benchmarks, max assets, illiquid assets never ranked, top N of the daily ranking, params), `test_screener` also covers the asset types (`KindsTest`: one ranking per type, ETF clones, fixed-income ETF, BDR weights, adjusted prices for funds; `AssetKindTest`: `asset_kind`, `drop_bad_candles`), `test_server` (real HTTP server on a free port: routes, private files, origin check, error statuses) and `test_browser` (published version: `runtime.BROWSER` patched, `FakeWorker` simulates `/db` and `/proxy`, scan in steps). Run them after any change and add a test for new rules or routes; never point a test at the real `data/`.
- **Calculations**: import the modules from the package (`from marketpressure import screener, portfolio as pf, core, market_data`). To test offline or reproducibly, replace `market_data.raw_history` with a function that returns saved Yahoo responses, and pass `as_of`/`now` (or patch `time.time`) to fix the clock: `session_in_progress`, `closed_for` and `today_iso` depend on it.
- **API**: run the server on another port with test files, without touching the real data:
  ```python
  import shutil
  from http.server import ThreadingHTTPServer
  from pathlib import Path
  from marketpressure import database, server
  shutil.copytree("data", "tmp/data")                 # a copy of the database
  database.DATA_DIR = Path("tmp/data")
  database.BACKUP_DIR = Path("tmp/data/backup")
  ThreadingHTTPServer(("127.0.0.1", 8766), server.Handler).serve_forever()
  ```
  Or simply: `MARKETPRESSURE_PORT=8766 MARKETPRESSURE_DATA_DIR=tmp/data python server.py`. If you test against the real database, back up the `data/` folder first and restore it afterwards.
- **Pages**: the scripts can run headless in Node (e.g. jsdom) with `fetch` redirected to the test server. Evaluate `core.js` and the page script **in a single eval** (in the browser, classic scripts share the global scope, including top-level `const`), and polyfill `innerText` (jsdom doesn't implement it).

## Publicação (Cloudflare)

Published as one Cloudflare Worker (`wrangler.jsonc`, deployed from GitHub by Workers Builds with `npx wrangler deploy`), with no Python server and nothing running on the user's machine:

- **Build** (`scripts/build.mjs`, run by wrangler before each deploy): copies `web/` to `dist/` (plus `index.html` = the Screener), copies Pyodide from the `pyodide` npm package (pinned in `package.json`) to `dist/pyodide/` (`pyodide.mjs`, `pyodide.asm.mjs`, `pyodide.asm.wasm`, `python_stdlib.zip`, `pyodide-lock.json`; same origin, so no CDN that a corporate network or blocker can bar), copies the package to `dist/py/marketpressure/` (except `server.py` and `__main__.py`) and writes `dist/py/manifest.json` (`version` = content hash, used as `?v=` to bust the cache). The Python code is public there; it holds no secrets.
- **Browser**: `core.js` sends `/api/*` to `py-worker.js` (Pyodide v314.0.7, Python 3.14), which runs the same `api.py` routes, so every calculation is still Python. The first visit downloads Pyodide (~13 MB, cached afterwards). Each page has its own Worker, so switching tabs reloads Python (a few seconds).
- **Worker** (`worker/index.js`): serves `dist/` (`ASSETS`; `/carteira` → `carteira.html` by the default `html_handling`), `/proxy?url=` (a POST is accepted only for Yahoo's screener, `YAHOO_SCREENER`: the Worker gets the fc.yahoo.com cookie and the crumb, keeps them for an hour per isolate and retries once with a new session on 401/403; GET only for the hosts in `SOURCES`: Yahoo, brapi, BCB, B3; adds the `BRAPI_TOKEN` secret to brapi URLs; sends no `Accept` header, because with `application/json` B3 wraps its JSON in a string (`b3_call` also unwraps it); cached at the edge for the same TTLs as the Python cache) and `/db` (`GET ?names=a,b` returns `{name: rows | null}` with each table's text inlined as stored, so NaN survives; `PUT {backup, tables: {name: "JSON text"}}` writes them in one `batch`; writes from another `Origin` get 403). The free plan's 10 ms CPU limit is why nothing is computed in the Worker.
- **Screener scan in the browser**: there are no threads, so `browser.py` replaces `scan_job.start` with a flag; after answering a request, `py-worker.js` sees it (`take_scan_request`) and runs `scan_begin` (universe; returns its size), then for each batch of 8 `scan_prepare(start, end)` (reads the batch's saved histories from D1 in one `/db` request, `prefetch_stored`, and returns each ticker's Yahoo URL for only what is missing, or null when nothing is fetched: still in the memory cache, or saved up to date outside session hours), fetches them in parallel through `/proxy`, hands them in with `prime` and calls `scan_step(i)` for each, then `scan_end` (`ScanJob.finish`/`fail`). Between batches the page's polling of `/api/scan` gets the progress. The scan is saved in D1 like on the server, so a visitor within 120 min reuses it (read when Python starts, and read again by `ScanJob._reload` before deciding to scan, so a newer scan saved by the update is picked up); during the session the update saves one every 30 min and outside session hours the daily update's scan is used, so normally nobody scans in the browser (slow on phones: it downloads every history).
- **Daily update** (`marketpressure/update.py`, `.github/workflows/atualizacao-diaria.yml`): GitHub Actions runs `python -m marketpressure.update` at 21:30 UTC (18:30 in São Paulo) Monday to Friday, every 30 min during the session (`7,37 13-20 * * 1-5`: 10:07 to 17:37 in São Paulo; histories are already up to date, so it only fetches the live candle and saves a scan that includes it), or by hand (Actions → Atualização diária → Run workflow). GitHub may delay schedules (once by ~3 h), which is why the browser TTL is longer. It loads BOVA11 and USDBRL and runs `run_scan` (each universe history gets its missing candles and is saved), then `write_scan`; exit code 1 on failure. With `MARKETPRESSURE_REMOTE_URL` (the site) and `MARKETPRESSURE_SERVICE_TOKEN` it calls `runtime.use_remote`, so everything goes through the Worker (`/proxy`, `/db` on D1), like the browser; without them it uses the local `data/` and the sources directly. The repository secret `MARKETPRESSURE_SERVICE_TOKEN` has the same value as the Worker secret `SERVICE_TOKEN` (locally in `.dev.vars` for `wrangler dev`). The Worker accepts `Authorization: Bearer <SERVICE_TOKEN>` (compared through SHA-256 + `timingSafeEqual`) only for `/proxy` and for the shared tables of `/db` (others 403, other paths 404). Holidays are not known: on a holiday and the session after it, saved histories look one session behind and each load asks Yahoo for `1mo` instead of nothing/`5d`, until the next daily update saves a new candle.
- **Login** (`worker/auth.js`; the Worker is the security boundary, since the Python runs in the untrusted browser, so this is the one place where rules live in JS). `wrangler.jsonc` has `run_worker_first: true`, so every request passes through the Worker: without a session, pages (GET with `Accept: text/html`) redirect to `/login?next=…` and everything else (`/db`, `/proxy`, `/pyodide/*`, `/py/*`) gets 401; only `PUBLIC` (`/login`, `styles.css`, `login.js`, favicon) is open. Any non-GET with a foreign `Origin` gets 403. Login by CPF (digits, check digits validated) or e-mail (lowercase) + password; **there is no sign-up**: only the admin creates accounts (page Conta, or `scripts/create-user.mjs`). Passwords: PBKDF2-SHA256 with salt, `ITERATIONS` = 10,000 (≈4.5 ms of CPU; the free plan's limit is 10 ms per request), stored as `pbkdf2_sha256$iter$salt$hash` so the count can be raised later. Sessions: random token in the `mp_session` cookie (HttpOnly, SameSite=Lax, Secure on https, 30 days); D1 keeps only its SHA-256 (`mp_sessions`). 5 failures in 15 min per login or per IP → 429 (`mp_login_attempts`). Routes: `POST /auth/login {login, password}`, `POST /auth/logout`, `GET /auth/me` → `{name, email, admin}`, `POST /auth/password {current, password}` (closes the user's other sessions), and admin only: `GET /auth/users`, `POST /auth/users {name, cpf, email, password}` (always a regular user; there is one admin), `POST /auth/users/password {id, password}`, `DELETE /auth/users?id=` (also deletes the user's sessions and portfolios; the admin can't be deleted). Passwords have 8–128 characters. `core.js` re-checks `/auth/me` after any API error and sends an expired session to the login page.
- **Data per user**: `/db` stores the portfolio tables as `{user id}/{table}` in `mp_tables`/`mp_backup`; the screener tables (`SHARED_TABLES` in `worker/schema.js`: `universe`, `scan`, `scan_failures`, `scan_analyses`) and the saved histories (`SHARED_PREFIX` `history_`, `isShared`) are shared. Table names match `[a-z0-9_]{1,40}`. The Python doesn't know about it (it asks for the plain table names). A new table is per user unless added to `SHARED_TABLES`.
- **Creating an account from the command line**: `node scripts/create-user.mjs --name "…" --cpf … --email … [--admin] [--remote] [--claim-legacy]` (password from `MP_PASSWORD` or a hidden prompt; default is the local D1 of `wrangler dev`, `--remote` needs `npx wrangler login`). `--claim-legacy` moves the portfolio tables saved before login existed (names without `/`) to the new account. Personal data and passwords never go into the repository.
- **Settings**: D1 database `market-pressure` (its id in `wrangler.jsonc`; tables in `worker/schema.js`, created on first use), the `BRAPI_TOKEN` secret (Worker → Settings → Variables and Secrets; locally `.dev.vars`, not versioned) and the custom domain route `marketpressure.lucasaraujo.dev.br` (needs the `lucasaraujo.dev.br` zone active on Cloudflare, with the registro.br nameservers pointing to it).
- **Testing the published version locally**: `npm install`, then `npm run dev` (builds and serves on `http://127.0.0.1:8787` with a local D1 in `.wrangler/`). The pages detect port 8787 and use the Python in the browser. The local D1 needs its own account (`create-user.mjs` without `--remote`) to get past the login.
